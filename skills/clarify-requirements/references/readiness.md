# Requirements readiness

Apply this rule in every project profile, including unconfigured projects, to
requirements capture, investigation, specifications, issue work, planning,
implementation, and a request to act after discussion.

Treat **95% confidence** as a practical stop signal about the intended outcome,
scope, authorization, data safety, and observable acceptance criteria. It is an
agent judgment about understanding the request, not a calculated probability or
certainty about a solution or root cause. A clear initial request can suffice.

Use the current request, settled discussion, established user preferences, and
repository evidence before asking. Ask only when plausible answers would
materially change the outcome, scope, authorization, data safety, or acceptance
criteria. Choose conventional, reversible defaults for low-impact choices.
When a material choice remains, ask the smallest focused blocking group,
normally in one round; ask again only if an answer reveals a new material
choice. Do not turn a low-impact preference or requirements summary into an
approval gate.

While an answer is pending, continue useful read-only investigation but hold
dependent edits, issue/PR writes, and other mutations. Silence and elapsed time
never supply an answer. At or above the threshold, briefly state the understood
scope or assumptions when useful and proceed without confirmation. Reuse settled
requirements across skills; reopen clarification only for a material change or
new ambiguity that lowers confidence below the threshold.

An unknown reproduction or root cause may remain explicitly unknown in a clear
investigation or issue-capture task. Distinguish observed behavior from intended
behavior in existing-project specifications. Readiness does not authorize actions
outside the user's requested workflow or replace a separate artifact preview or
approval rule.
